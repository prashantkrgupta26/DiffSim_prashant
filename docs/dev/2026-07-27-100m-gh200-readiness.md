## 1. Target definition — what "100M DOF" is concretely

The monolithic NS-SBM VMS saddle is node-major interleaved `[u_1,u_2,u_3,p]`,
**ndof=4** per free node (`[R2b]` §2). So:

- **100M DOF ⇒ ~25M free nodes.**
- A uniform octree at level L in 3-D has `(2^L+1)^3` nodes. **L8 uniform =
  2,115,937 nodes = 8.46M DOF** (`[RUNBOOK-3D]` Task-8b table; measured as the L7
  ladder rung — note the runbook labels the 2.1M-node rung "L7" in the ladder
  driver's convention). 25M nodes is between uniform L8 (2.1M nodes) and L9
  (16.9M nodes) — i.e. **100M DOF is not reachable by a uniform mesh below L9;
  it is an ADAPTIVE-mesh target** (base coarse + banded refinement around the
  shell/wake, exactly the `build_adaptive_plate_mesh` / `build_adaptive_cube_channel`
  pattern of `[RUNBOOK-3D]` Phase 1b/2).

**nnz at the 27-point stencil, ndof=4.** The 100M-DOF PPE (scalar, ndof=1) is
quoted at **2.7 billion nnz for 100M DOF at a 27-pt stencil** (`[AMGX]`
empirical probe: `nnz for 100M DOF (27-pt) = 2,700,000,000`). That is the scalar
Poisson operator. The monolithic saddle has a 4×4 node-pair block: a full
element-graph superset block is 16× denser per node-pair. The device assembler
builds the **fixed element-graph SUPERSET** (every ndof×ndof node-pair block
dense) — measured to be a real fill penalty vs the pruned host `TᵀKT` in 3-D
(`[M5]` §4 "MEASURED NUANCE"). For a 25M-node saddle with ~27 node-neighbors,
superset nnz ≈ 25M nodes × 27 neighbors × 16 = **~10.8 billion nonzeros**. This
is the number the CSR memory ledger must carry.

**Memory ledger (single-card, 95 GiB HBM budget).**

| Object | Size model | 100M-DOF value | Source |
|---|---|---|---|
| Solution + RHS + a few Krylov vectors (fp64) | ndof·nodes·8 B each | 0.8 GB per 100M-DOF vector | direct |
| **Stored saddle CSR values (fp64)** | superset_nnz·8 B | **~86 GB** (10.8B nnz) | `[M5]` §4 superset model + `[AMGX]` nnz basis |
| CSR indices (int32) | superset_nnz·4 B | ~43 GB (int32) / ~86 GB (int64) | `[HORIZON]` §1 "2.2 GB/M dofs int32" |
| Direct factor (cuDSS) | ≫ CSR (superlinear fill) | **does not fit** — see §3 | `[LEDGER]` Task-8b, `[R2b]` §1 |
| Matrix-free J·v GP-field buffers | grads [ngp,ndof,dim] dominate | ~measured 39 GB at 84.5M film DOF | `[MATFREE]` §4 |

**Immediate conclusion from the ledger:** the stored monolithic saddle CSR
(values ~86 GB + indices ~43 GB int32 = ~129 GB) **does not fit in 95 GiB HBM at
all**, and a direct factor of it is categorically out (§3). The 100M-DOF solve is
**matrix-free + iterative or it does not run on one GH200.** Everything in §2–§5
follows from this.

## 2. The pipeline, stage by stage

Each stage: current MEASURED capability → the wall → gap to 100M → candidate fix
(effort S ≤ days / M ≤ weeks / L ≤ months) and the existing machinery it builds
on.

### 2.1 Mesh build (octree → nodes → conn → boundary)

- **Measured capability.** Adaptive: r6b9 (base-L6 / band-L9) thin-plate mesh
  builds and marches on GH200 at 13.7 GiB GPU, 22.21 s/step (`[RUNBOOK-3D]`
  Phase-2 table). Uniform closed-form: **L7 (2.1M DOF) mesh+constraints
  45.7 s → 0.80 s (57×); L8 (17M DOF) 7.5 s; projected L9 (135M DOF) ~60 s**
  (`[CLOSEDFORM]` commit body — the 17×/20× figure is mesh-only, ~3000× on
  constraints which become free).
- **The wall.** The **HOST adaptive mesh-build wall**: r7b9 (base-L7 tree +
  band-L9 refinement) hit **MaxRSS 209.7 GB > the 200G cgroup → oom_kill (exit
  137), GPU idle at 13.5 GiB** (`[LEDGER]` Task-8b wall (b); `[RUNBOOK-TS]` §6.2;
  `[RUNBOOK-3D]` Three-Wall Analysis §2). This is the host-side
  octree/mesh/constraints build (`np.unique`/`np.isin`/`np.sort` in `nodes.py:83`
  and `constraints.py`), single-threaded, and it dies on RAM, not on GPU.
- **Gap to 100M.** r7b9 is roughly a 10M-DOF-scale adaptive build (base-L7 tree
  ≈ 2M-node uniform envelope + band-L9 refinement). It already needs **209.7 GB
  host RSS**. The 100M-DOF adaptive target is ~10× larger in node count; the
  general-path build memory is dominated by transient `np.unique(all_ic, axis=0)`
  intermediates (`nodes.py:162`) that scale with the pre-dedup element-corner
  count. **A naive 10× scale ⇒ multiple TB — far past Grace's ~480 GB.** The
  closed-form fast path does NOT cover this: `[CLOSEDFORM]` triggers ONLY for a
  complete uniform `(2^L)^dim` tree; **adaptive/carved/mixed-p fall through to the
  unchanged general (np.unique) path** (commit body, explicit). The 100M target is
  adaptive (§1) ⇒ the closed-form win does not apply as-is.
- **Candidate fixes.**
  1. **Raise `--mem` toward Grace's ~480 GB (S).** sbatch `--mem` is raisable off
     the 200G cgroup toward the Grace socket limit (`[LEDGER]` Task-8b mitigation;
     `[RUNBOOK-TS]` §6 "raise --mem toward 480 GB"). Buys ~2.3× headroom — gets
     r7b9 to fit, does NOT reach 100M. Necessary, not sufficient.
  2. **Extend the closed-form arithmetic build to GRADED regions (L).** The
     closed-form node/conn indexing (`_build_uniform_fast`, `nodes.py:85`,
     `li*strides` arithmetic) is exact for a complete level. A banded-adaptive
     mesh is a union of complete-level blocks with hanging-node seams. Building
     each band arithmetically and stitching seams via explicit hanging-node
     constraints (the constraint machinery already exists, `[BLUEPRINT]` §3)
     avoids the global `np.unique`. Builds on `[CLOSEDFORM]` + hanging-node
     constraints. This is WP1 (§5).
  3. **Streaming / chunked build (M–L).** Build the node set in axis-0 slabs
     (the lexicographic slab partition is already proven for solve —
     `[NCCL]` `partition.py` "row-block slab partition == geometric slab"), dedup
     per-slab with only halo-plane overlap, never materialize the global
     pre-dedup corner array. Bounds transient RSS to one slab.

**WP0 RESOLUTION (2026-07-27, Grace job 11771926): the adaptive mesh build is EXONERATED.** The exact r7b9 case (base L7/band r9, 2.31M nodes / 9.24 M-DOF) builds in **3.71 GB peak, 94 s** on Grace (0.40 GB/M-DOF; L6/r9: 0.89 — sublinear per-DOF). The 209.7 GB OOM was CROSS-LEG ACCUMULATION in the single-process GH200 ladder (prior legs' assembled CSRs + the failed L7-uniform cuDSS factorization's host staging), mis-attributed to the build because the job died during that leg with the GPU idle. Mesh build extrapolates to ~40-90 GB at 100M DOF — inside Grace. The streaming build reclassifies to the medium-term remeshing/mixed-p architecture; the 100M critical path is the solver (R2b saddle preconditioner / matrix-free).

### 2.2 Constraints (hanging-node + Dirichlet)

- **Measured capability.** Constraint build is **0.23 s at 3-D L5** — the
  migration rule says **do NOT migrate it** (`[BLUEPRINT]` §1 profile table). On
  a complete uniform grid the constraint operator is the identity and is
  short-circuited to T=I, effectively free (`[CLOSEDFORM]`). Constraint-aware
  device scatter is PROVEN on adaptive hanging-node meshes: **device constrained
  assembly == host TᵀKT at 1e-12 on a hanging-node mesh** (`[BLUEPRINT]` §3;
  `[LEDGER]` ThinShell Task-4/5 "csr_slots covers all Af_c entries, 56 hanging
  nodes, parity 1e-9"; 3-D adaptive L3/refine4 parity GREEN).
- **The wall.** For adaptive meshes the constraint build shares the host
  `np.unique`/`np.isin` cost (`constraints.py:70,77,78`) folded into the §2.1 RSS
  wall — it is NOT independently the bottleneck, but it rides the same
  general-path memory.
- **Gap to 100M.** None structural — the machinery exists and is parity-locked.
  The gap is the shared host-RSS wall of §2.1.
- **Candidate fix.** On-the-fly constraint generation during the chunked build
  (fix 3 above): emit hanging-node constraints per band-seam as bands are built
  (S once WP1's streaming build exists). Builds on `[BLUEPRINT]` §3
  constraint-aware scatter, which already resolves master chains to free nodes.

### 2.3 Shell classify + two-sided extract

- **Measured capability.** 3-D two-sided shell assembly (`sbm_vector_dirichlet_twosided`
  + `surrogate_traction`) RUNS with dim=3 on the adaptive hanging-node mesh
  (`[SPEC]` T1a/T1b were the named blockers; `[LEDGER]` ThinShell Task-5 clears
  them: "3-D device assembly incl. adaptive L3/refine4 parity GREEN"). The
  `FiniteSheet` oracle serves BOTH classify and extract (fixed patch normal as
  `n_grad`) — no separate Plane oracle needed in 3-D (`[RUNBOOK-3D]` Physics
  notes). Two-sided face extraction is **host-side per epoch** (`[LEDGER]`, anchor
  in the brief) — O(surface) work.
- **The wall.** Two-sided face extraction is host-side and per mesh-epoch;
  face count scales with the RESOLVED shell area / h² (§4). At the r6b9 rung the
  excluded/intercepted count was 33,800 (`[RUNBOOK-3D]` Phase-2 `n_excluded`);
  at r7b9 the job never reached this stage (died in the host mesh build, §2.1).
- **Gap to 100M.** The extract itself has not been exercised at 100M-mesh face
  counts — it is gated behind the §2.1 mesh-build wall. Face count is O(shell
  area / h²); see §4 for the scaling number.
- **Candidate fix.** Extraction is O(surface) and host-computed then
  slot-scattered — the same "host-computed per iterate, slot-scattered" hybrid the
  film face-terms use, measured **< 10% of step time** at 2-D L7 (`[M5]` §1 face
  terms). Effort S to confirm at scale once the mesh build clears; only migrate
  to device if it shows in a scale profile (`[BLUEPRINT]` §1 migration rule).

### 2.4 Assembly

- **Measured capability.** Device slot-map scatter: **assembly per call 52–255×
  vs host** (2-D), **84–112× in 3-D**; the march is SOLVER-BOUND on the device
  path everywhere (`[M5]` §4). Numeric fill is already device (warp kernels);
  the migrated piece is the values round-trip + scatter (`[BLUEPRINT]` §1).
  Constraint-aware weighted scatter proven on hanging nodes (§2.2).
- **The wall.** Two independent walls at scale:
  1. **Stored-CSR memory** — the superset saddle CSR is ~129 GB at 100M DOF
     (§1 ledger). It does not fit in 95 GiB. So assembly-to-a-stored-CSR is dead
     at 100M on one card; assembly must feed a **matrix-free J·v** (§2.5/§3).
  2. **int32 nnz** in any index-32 consumer (AMGX at ~79.5M DOF, `[AMGX]`) — a
     stored-CSR path would also overflow int32 indices (~10.8B nnz ≫ 2^31).
- **Gap to 100M.** The matrix-free assembler exists and is proven: the
  `matvec_only=True` path builds ONLY bins + device conn + GP/Ae buffers, **NO
  CSR pattern, NO indices, and crucially NO int32-nnz ceiling** (`[MATFREE]` §4).
  Measured: **live J·v at 84.5M DOF (film, M=3,K=2) runs in 39.1 GB on a 48 GB
  card**, apply cost FLAT at ~4.1–4.2 µs/element across a 64× scale span. The gap
  is that the matrix-free outer has been proven for the multiphase (M,K) system,
  **not yet wired for the NS-SBM saddle with two-sided shell face terms** — the
  face-term Jacobian correction pattern exists (`_build_face_jac`, `[MATFREE]` §1)
  but for the film top-flux block, not the shell Nitsche block.
- **Candidate fix.** Port `apply_Jv` + `apply_batch_matvec` to the NS-SBM element
  kernels and add the two-sided-shell face block as the x-independent host CSR
  correction (mirroring the film face-Jac path). Effort M — the operator, the
  batch matvec, and the parity harness all exist (`[MATFREE]` §1–2); the shell
  face block is the new physics piece.

### 2.5 Solve — the crux (own section §3)

- **Measured capability.** Direct cuDSS: fits ≤ **1.08M–2.9M saddle DOF** on
  GH200 (§3). Iterative: fused device BiCGStab converged on an **L6 monolithic
  saddle (~1M DOF, 3-step march)** (`[RUNBOOK-TS]` §6.3) but DIVERGED on the 2-D
  Re=250/L9 Oseen predictor (relres 2.3e15, `[LEDGER]` Task-7 preflight).
  Matrix-free outer FGMRES proven to 84.5M DOF (film, `[MATFREE]`). NCCL 2-GPU
  CG proven SPD at L4/L5 (`[NCCL]`).
- The full solver analysis is §3.

### 2.6 Observables (Cd / St)

- **Measured capability.** Three independent force functionals now exist and are
  cross-validated at Re=250 2-D: surrogate traction (`surrogate_traction`,
  bare σ·n on shifted faces), CV momentum-deficit drag, and the
  consistent Nitsche reaction `Cd_rxn = -wᵀ(Af_c x - bf_c)` (`[LEDGER]`
  Leak-Drag + Traction-Dissection ledgers; `[RUNBOOK-TS]` §5 verdict).
- **The finding that governs scale.** **The penalty term carries ~96–97% of the
  consistent reaction at α=50 at EVERY resolution leg** (D1–D4: penalty 2.53 of
  2.60, …, 2.37 of 2.43; `[RUNBOOK-TS]` traction-dissection table). The surrogate
  reads **2.3× the consistent reaction**; bridge ratio (bare σ·n vs consistency
  class) is 49–77, far from 1 — bare σ·n and the consistency term are categorically
  different objects. Force is α-sensitive (+36–41% over α 20→100).
- **Gap to 100M.** The observable question is physics, not scale — but any
  "hero force" claim at 100M inherits the α-sensitivity and penalty-dominance
  caveats. See §4.

## 3. The solver at 100M on ONE GH200 (95 GiB) — what fits

### 3.1 Direct is dead — measured, not assumed

cuDSS on GH200 fits **between ~1.1M and ~2.9M saddle DOF**: 1.08M (uniform L6,
~51 GiB transient factor) fits; **2.92M (adaptive a6r9) fails after climbing to
78.3 GiB resident; 8.46M (uniform L7) fails early at ~35 GiB** (`[LEDGER]`
Task-8b wall (a); `[RUNBOOK-TS]` §6.1; `[RUNBOOK-3D]` Three-Wall §1). 100M DOF is
**34–90× past the measured cuDSS wall.** The direct factor of the ~129 GB stored
CSR would need far more than 95 GiB of fill. **Direct is out; the solver MUST be
iterative.** (`[R2b]` §1 confirms: L6 1.09M cuDSS `ALLOC_FAILED` at Re=100.)

### 3.2 What fits: matrix-free iterative, with the honest UNPROVEN list

**The fits-math (from `[MATFREE]` §4, the horizon-readiness math).** The
matrix-free J·v at 84.5M film DOF (M=3,K=2, ndof=10) measured **39.1 GB GPU on a
48 GB card**, dominated by the eval-x-once GP-field buffers
(`_grads_dev [ngp,10,3]` = 16.1 GB at ngp=67.1M). The NS-SBM saddle is
**ndof=4** (vs film ndof=10) — the per-node GP buffers are ~2.5× lighter per
node. So a 100M-DOF (25M-node) NS-SBM matrix-free J·v is projected to fit
**well inside 95 GiB HBM** (the film 84.5M-DOF case at ndof=10 already fit in
39 GB; the NS case is lighter per DOF and 95 GiB is 2× the card that measurement
was taken on). This is a projection off `[MATFREE]` §4, not a measurement at
NS-SBM 100M — flagged.

**Mixed precision.** fp32-factor + FP64 iterative refinement is measured **2–8
refinements, a net loss on Ada (structure-bound), profitable where FLOP-bound —
Blackwell-at-scale is that regime** (`[HORIZON]` §2 item 6, finding 8j). The GH200
matrix-free apply is bandwidth-bound (`[MATFREE]` §4 "apply is spmv/bandwidth-
bound"), so fp32 storage of the GP-field buffers would ~halve the dominant memory
term and roughly double throughput — a real lever, UNMEASURED for NS-SBM.

**Out-of-HBM via C2C.** The GH200's NVLink-C2C coherent memory (~900 GB/s,
unified address space) makes host↔device transfers cheap (`[SPEC]` "GH200
reframing"). For **Warp-owned arrays**, `wp.set_device_allocator` +
`CudaManagedAllocator` (the film `--managed` lever, `cluster/gh200_osub.sh`) can
oversubscribe HBM into Grace LPDDR — the oversubscription probe rungs are
110/130/150% of effective HBM for a ~35 GB working set. **This is the C2C
question for iterative operands:** the matrix-free J·v operands (GP-field buffers,
Krylov vectors) ARE Warp-owned arrays ⇒ the managed lever DOES apply to them, so
a J·v working set that slightly exceeds 95 GiB could spill to Grace at C2C
bandwidth. **UNPROVEN for the NS-SBM J·v specifically** — the managed lever was
measured on the film capacity probe, not this operator.

### 3.3 The honestly-UNPROVEN list at scale

1. **The R2b saddle block-preconditioner does not scale.** `BlockAMGPreconditioner`
   converges on a tiny L3 saddle (rel 1.9e-8) but **CLIFF-FAILS at L5 (143k DOF):
   2000+ FGMRES iterations, no convergence**, and does NOT respond to
   strengthening F, swapping the Schur, or raising restart (`[R2b]` §0, §4). A
   cliff = STRUCTURAL/scale-specific failure. **There is no proven scalable
   preconditioner for the monolithic NS-SBM saddle above ~143k DOF.** This is the
   single biggest solver risk at 100M and is UNRESOLVED (the handoff's H1–H5
   hypotheses were parked).
2. **Fused BiCGStab at scale is a 3-step result.** L6 (~1M DOF) monolithic fused
   converged in **3 steps only; long-march stability UNCONFIRMED** (`[RUNBOOK-TS]`
   §6.3) — and the SAME solver DIVERGED on the 2-D Re=250/L9 Oseen predictor
   (`[LEDGER]` Task-7 preflight). Convergence is conditioning-dependent and
   unproven for a 100× larger saddle.
3. **cuDSS oversubscription needs `cudssDeviceMemHandler`** — the film `--managed`
   lever does NOT transfer to cuDSS (it allocates factors internally via nvmath;
   observed C2C behavior at the wall was **clean fast-fail ALLOC_FAILED, no
   spill, no crawl** — GH200+cuDSS is binary fit/no-fit; `[LEDGER]` Task-8b
   oversubscription decision; `[RUNBOOK-TS]` §7 item 3). **This is IRRELEVANT at
   100M because there is no direct solve** — noted so it is not chased.
4. **NCCL multi-GPU is single-node-only on `nova-arm`.** The NCCL 2-GPU CG is
   proven SPD at L4/L5 (`[NCCL]`), but nova's GH200 partition is a **single-GPU
   node** (`[NCCL]` Next-steps 1: "Nova's GH200 partition `nova-arm` is a single
   GPU node — good for a single-GPU capacity run, not multi-GPU scaling"). So on
   ONE GH200 the 100M solve is single-GPU; multi-GPU NCCL scaling needs a
   multi-GPU node (A100 4–8/node, or Horizon GB 2-GPU/node) and is NOT available
   on the stated target. The 100M-on-ONE-GH200 path is therefore **single-GPU
   matrix-free iterative**, not distributed.
5. **AMGX single-rank int32 nnz overflows at ~79.5M DOF** (`[AMGX]`, hard C-ABI
   limit, no 64-bit flag) — below 100M. AMGX as the single-rank preconditioner is
   out at 100M; distributed AMGX needs MPI + multi-rank (multi-GPU node, per (4)).

**Solver verdict for 100M on ONE GH200:** the only path that fits the memory
ledger is **matrix-free outer Krylov (FGMRES/BiCGStab) with a matrix-free J·v** —
and its convergence is the UNPROVEN crux, because the one preconditioner built for
this saddle (`[R2b]`) cliff-fails at 143k DOF. The PPE-based projection route
(SPD Poisson → `gpu_cg`/NCCL-CG, `[NCCL]`) is the numerically de-risked
alternative, BUT the projection split **diverges at Re=250/L9 in 2-D and carries
a ~40% 3-D gap** (`[RUNBOOK-TS]` §5; `[LEDGER]` O6 "projection diverged under
corrected config, structural"), so it is not a drop-in for the shedding regime.
**Monolithic is the proven engine; matrix-free is the only way to run it at 100M;
its preconditioner is unproven at scale.**

## 4. Thin-shell specifics at scale

- **Two-sided face count scaling.** Face count ∝ resolved shell area / h². At the
  r6b9 rung (band-L9, h_fine = 1/512-class) the intercepted count was **33,800
  faces** (`[RUNBOOK-3D]` Phase-2 `n_excluded`). The adaptive lever is strong
  here: a5r8 reaches near-wall **h = 1/256 (uniform-L8 territory, ~67M DOF-
  equivalent near-wall resolution) at only 626K DOF** — "the adaptive lever buys
  ~2 orders of magnitude on near-wall resolution per DOF" (`[RUNBOOK-3D]`
  Phase-1b). So a 100M-DOF adaptive mesh could carry a shell resolved to
  h ~ 1/1024–1/2048; face count scales as h⁻² over the shell patch. For a unit-
  domain plate of area ~0.06 at h=1/1024, that is O(0.06·1024²) ≈ **~65k faces**
  — same order as r6b9, not a blow-up, because the shell is a 2-D manifold in a
  3-D mesh (face count grows one dimension slower than DOF).
- **Host extraction cost.** Two-sided extraction is host-side per epoch, O(surface).
  At the face counts above it is comparable to r6b9's 33,800 — and the analogous
  host-computed-then-slot-scattered face-term work is **< 10% of step time** at
  2-D L7 (`[M5]` §1). Extraction is NOT projected to be the scale bottleneck; the
  MESH BUILD around it is (§2.1). Confirm at scale once WP1 lands (effort S).
- **The observable question given penalty-dominance.** At 100M the same physics
  finding holds: **the reaction is ~96–97% penalty virtual work at α=50**
  (`[RUNBOOK-TS]` traction-dissection). Any hero Cd at 100M is an α-scaled penalty
  functional. The resolution trend is **monotone toward literature but with
  NON-shrinking increments (Cd_rxn 2.60→2.81→3.05 across r9→r10→r11) — pre-
  asymptotic, mesh-convergence NOT demonstrated** (`[RUNBOOK-TS]` traction-
  dissection resolution rule; `[LEDGER]` TD-4 D3). **So a 100M-DOF run would be
  the natural next resolution rung to test whether the increments finally shrink**
  — that is arguably the strongest SCIENCE justification for the 100M hero, but
  the force it reports must be quoted as the consistent Nitsche reaction (not the
  surrogate, which reads 2.3× high) with the α-sensitivity caveat attached.

## 5. Recommended attack sequence (workpackages + acceptance gates)

Ordered; dependencies noted. Effort classes S/M/L per §2.

### WP1 — Memory-lean adaptive mesh build (S-config + L-algorithm). **No dependency; do first.**

**Why first.** The r7b9 host mesh-build OOM (209.7 GB > 200G) is the binding
constraint on the entire 100M path (`[LEDGER]` Task-8b wall (b)); every later
stage is gated behind it. The GPU is idle at 13.5 GiB when the job dies — this is
purely a host-RAM/algorithm problem.

**Concrete memory requirement.** The adaptive builder must hit a **host RSS
budget of ≤ ~15 GB per 10M-DOF-scale adaptive build** to reach 100M within
Grace's ~480 GB (target: 100M-DOF adaptive build in **≤ ~150 GB host RSS**,
i.e. ~1.5 GB/M-DOF, comfortably inside Grace's 480 GB with headroom for fields).
Anchor: r7b9 (~10M-DOF-scale) currently needs **209.7 GB** — i.e. ~14× over the
required per-DOF budget. The general `np.unique(all_ic, axis=0)` path
(`nodes.py:162`) is the offender; it materializes the full pre-dedup corner array.

**Algorithmic options (in preference order).**
1. **Closed-form graded build** (L) — extend `_build_uniform_fast`
   (`[CLOSEDFORM]`, `nodes.py:85`) from a single complete level to a UNION of
   complete-level bands, numbering each band arithmetically and emitting
   hanging-node constraints at band seams (constraint machinery exists,
   `[BLUEPRINT]` §3). Kills the global `np.unique`. Highest payoff, most work.
2. **Streaming / chunked slab build** (M–L) — build in axis-0 slabs (the proven
   `[NCCL]` slab partition), dedup per-slab with halo-plane overlap only, never
   materialize the global corner array. Bounds transient RSS to one slab.
3. **Raise `--mem` toward 480 GB** (S) — necessary immediate mitigation
   (`[LEDGER]` Task-8b); buys r7b9 to fit, does not reach 100M alone. Do this
   first as the unblock, in parallel with 1/2.
4. **Disk-backed intermediates** (M) — memmap the pre-dedup corner array; last
   resort, slow.

**Acceptance gate:** an adaptive (base-L7 / band-L9-class) mesh builds within
**≤ 150 GB host RSS** and the assembled system is **bit-for-bit identical to the
general-path build** (the `[CLOSEDFORM]` gate standard: node icoords/coords/conn/
boundary/conn_of identical, constraints == reference). Then: r7b9 completes on
GH200 (the run that OOM'd).

### WP2 — Matrix-free NS-SBM saddle operator with two-sided shell face block (M). **Depends: none (parallel to WP1); needed before any 100M solve.**

Port `apply_Jv` + `apply_batch_matvec` (`[MATFREE]` §1) from the multiphase
kernels to the NS-SBM element kernels; add the two-sided-shell Nitsche face block
as the x-independent host-CSR correction (mirroring `_build_face_jac`).

**Acceptance gate:** matrix-free J·v == stored-CSR J·v at **rel ≤ 1e-12** on an
adaptive 3-D shell mesh with hanging nodes and active two-sided faces (the
`[MATFREE]` §2 parity standard: they hit 1.13e-15 at 84.5M film DOF); and the
`matvec_only=True` setup builds with NO CSR/indices (no int32 ceiling).

### WP3 — Scalable preconditioner for the matrix-free saddle outer solve (L). **Depends: WP2. The crux.**

This is where `[R2b]` stalled. The block preconditioner cliff-fails at 143k DOF;
the handoff's H1–H5 (instrument the FGMRES residual curve; identity-vs-precond
comparison; full vs restarted GMRES; AMG-coarsening on SBM structure; PCD Schur)
are the parked leads. Fold in the matrix-free J·v (WP2) so the outer never needs
a stored A. Fallback: if the monolithic saddle stays un-preconditionable at
scale, pivot to the **projection PPE route** (SPD Poisson → `gpu_cg` /
single-GPU CG, `[NCCL]`) — but only after resolving the projection's structural
divergence at Re=250/L9 (`[RUNBOOK-TS]` §5 research track), which is itself open.

**Acceptance gate:** the matrix-free preconditioned outer solve converges
(rel < 1e-8, **mesh-independent-ish outer iteration count**) at L5 (143k, the
current cliff), then L6 (1.09M) — the `[R2b]` §8 definition of done — as the
staging gate before any 100M attempt.

### WP4 — Single-GPU 100M matrix-free capacity + oversubscription run (M). **Depends: WP1, WP2, WP3.**

Combine WP1 mesh + WP2 operator + WP3 preconditioner on one GH200. Use the
`--managed` C2C lever (`cluster/gh200_osub.sh`) for the Warp-owned J·v operands
if the working set exceeds 95 GiB (§3.2). Add fp32 GP-buffer storage
(`[HORIZON]` 8j) if memory-bound.

**Acceptance gate:** a 100M-DOF adaptive two-sided-shell NS-SBM step completes on
one GH200 with finite, physically-plausible Cd; peak HBM ≤ 95 GiB (or documented
managed spill to Grace within C2C bandwidth); step time recorded.

### WP5 — Observable at scale (S). **Depends: WP4.**

Report Cd as the **consistent Nitsche reaction** `Cd_rxn = -wᵀ(Af_c x - bf_c)`
(`[RUNBOOK-TS]` §5) — NOT the surrogate (reads 2.3× high) — with the
α-sensitivity and penalty-dominance caveats. Test whether the resolution
increments finally shrink at this rung vs r9→r11's non-shrinking trend
(`[RUNBOOK-TS]` traction-dissection). This is the science payoff of the hero run.

**Acceptance gate:** Cd_rxn reported with penalty-fraction breakdown and the
resolution-increment vs r11 recorded; observable-decision escalation (`[LEDGER]`
TD-4 middle-case) either resolved or advanced.

**Dependency graph:** WP1 ∥ WP2 → WP3 → WP4 → WP5. WP1's `--mem` bump and WP2 are
immediately startable; WP3 is the long pole and the genuine research risk.

## 6. Open questions for Baskar (genuine design forks only)

1. **Monolithic-matrix-free vs projection-PPE as the 100M solver spine.** The
   monolithic saddle is the PROVEN physics engine but has NO scalable
   preconditioner (`[R2b]` cliff at 143k). The projection PPE is numerically
   de-risked at scale (SPD → `gpu_cg`/NCCL-CG, `[NCCL]`) but STRUCTURALLY DIVERGES
   at Re=250/L9 and carries a ~40% 3-D gap (`[RUNBOOK-TS]` §5). Which do we bet
   WP3 on — solve the saddle preconditioner (research-grade, `[R2b]` H1–H5) or fix
   the projection split (research-grade, `[RUNBOOK-TS]` §5 suspects)? Both are open;
   we should fund ONE as primary.

2. **Single-GPU 100M vs multi-GPU.** `nova-arm` is a single-GPU node (`[NCCL]`).
   Do we target genuine single-GPU 100M (matrix-free + C2C oversubscription, this
   doc's WP4), or treat GH200 as the ARM on-ramp and target the 100M hero on a
   multi-GPU node (Horizon GB 2-GPU, or A100 4–8/node with distributed AMGX/NCCL,
   `[AMGX]` + `[HORIZON]`)? This changes WP3's target (single-GPU preconditioner
   vs partitioned multi-rank).

3. **How much does the closed-form graded build (WP1 option 1, effort L) buy vs
   streaming (option 2, M)?** Option 1 makes the 100M build ~free (like uniform
   L9's projected ~60 s, `[CLOSEDFORM]`) but is real algorithmic work on the
   band-seam constraint stitching; option 2 is more mechanical but leaves a
   per-slab dedup cost. Fork: is the memory-lean build a one-time capability
   investment (option 1) or a "make r7b9 fit now" tactical fix (option 3 + 2)?

4. **α policy for the hero observable.** The force is 96–97% penalty virtual work
   and α-sensitive (`[RUNBOOK-TS]` traction-dissection). Do we run the 100M hero
   at the standing α=50, or first resolve the α-scaling investigation
   (α~Pe·p² vs fixed 50, the standing follow-up) so the hero Cd is defensible?
   A 100M run at an un-adjudicated α produces a penalty-dominated number of
   uncertain physical meaning.
